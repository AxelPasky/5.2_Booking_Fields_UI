# Final Project: Frontend Development with AI Assistance

A presentation on the development of a React frontend for the `API_Fields_Booking` API, created with the assistance of an Artificial Intelligence model.

## Reflections on the Learning Process

This project was instrumental in familiarizing me with AI as a powerful development tool. Starting with no prior experience in React, it was fascinating to witness how carefully crafted prompts could be translated into functional, working code. The AI provided significant assistance with complex tasks like Dockerization and understanding the intricacies of connecting the frontend to a live API.

However, this approach is not without its challenges. As a newcomer to React, it became clear that using the AI effectively means treating it as both an assistant and a mentor. Asking targeted questions to understand the *why* behind the generated code is crucial. Relying on it passively, without this critical engagement, almost certainly leads to dead ends.

During the project, I encountered technical issues that seemed to stem from providing too much context, which occasionally confused the AI. I also observed that the AI, particularly within the VS Code Copilot chat, would sometimes appear to "reset," losing conversational memory or changing its coding style mid-task. This requires constant vigilance from the developer to avoid being led down the wrong path and losing time instead of gaining it.

Another key reflection is on the nature of learning itself. It's easy to fall into a vicious cycle where you let the AI do the work without truly understanding the output. I realized early on that maintaining high attention and actively questioning the AI's suggestions was essential. The goal must be to use this tool for **active improvement**—to learn and grow—rather than becoming a passive observer of code generation.

## 1. Selected AI Model and Rationale

### Selected Model
- **Artificial Intelligence:** Google's Gemini 2.5 Pro (Preview).
- **Interaction Tool:** GitHub Copilot Chat in Visual Studio Code.

### Rationale
I chose this combination for three main reasons:

- **Context-Awareness:** GitHub Copilot has full access to the source code of my Laravel backend. This allows it to generate frontend code (React components, API calls) that is already aligned with the existing routes, models, and data structures, minimizing manual integration work.
- **Specialization in Code Generation:** Gemini is a state-of-the-art LLM, optimized for writing and understanding code. It can translate complex requests into structured React components, manage state, and implement API interaction logic.
- **Iterative Development Process:** The Copilot chat interface facilitates a conversational development process. It's possible to start with a base generated by the AI and then refine it with subsequent requests, analyzing and modifying the code step by step.

## 2. Log of Key AI Interactions

This section documents the most significant prompts and the resulting code or solutions, showcasing the iterative development process.

### Interaction 1: Initial Setup & First Component
This interaction established the project's foundation and immediately highlighted the AI's ability to adapt to the backend's constraints.

**User Prompt:**
> I would like you to recommend the best AIs, available in GitHub Copilot, for creating the API's frontend. We will track our progress in this `PRESENTATION.md` file. I have already set up the development environment to use React.

**AI Response (Summary):**
The AI generated the first component, `FieldList.jsx`, to fetch and display sports fields from the `GET /api/fields` endpoint.

**User Correction:**
> The backend is not to be modified, it is correct as it is. To be able to see all the routes inside the middleware you have to be logged in, so for this reason it is not possible to see the fields without first being logged in. We have to work following this logic.

**Analysis:**
This was a crucial first step. The AI initially assumed the endpoint was public. The user's correction forced the AI to pivot, adding logic to the component to handle an unauthenticated state. This demonstrates the importance of human supervision to guide the AI according to the project's specific security rules.

### Interaction 2: Implementing Global State for Authentication
This was a major architectural step. Instead of managing login status in individual components, the AI was prompted to create a centralized solution.

**User Prompt:**
> It's time to work on the user authentication part as per point 1.3 of the to-do.md list. Write the code and explain it to me.

**AI Response (Summary):**
The AI explained the need for a global state and generated the `AuthContext.jsx`. This context provides a centralized place to store the user's token and information, along with the `login`, `register`, and `logout` functions, making them accessible throughout the entire application.

**Analysis:**
The AI generated a robust, standard solution for state management in React. This single interaction laid the groundwork for all subsequent authenticated features, from protected routes to user-specific data fetching.

### Interaction 3: Creating and Protecting Routes
With authentication in place, the next step was to secure parts of the application.

**User Prompt:**
> Now that the routes are protected, let's get user-specific data with the bookings.

**AI Response (Summary):**
The AI created the `ProtectedRoute.jsx` component, which acts as a "guardian" for pages, redirecting unauthenticated users to the login page. It then implemented the `MyBookingsPage.jsx`, placing it behind this protected route and using the token from `AuthContext` to fetch user-specific bookings from the `GET /api/bookings` endpoint.

**Analysis:**
This interaction shows how the AI can build upon previously generated features (`AuthContext`) to implement new, more complex logic like route protection and authenticated data fetching.

### Interaction 4: Implementing a Complex Feature - The Booking Form
This interaction demonstrates the AI's ability to handle a multi-step feature involving user input, API calls, and dynamic UI updates.

**User Prompt:**
> Now the form must be complete. At the moment there is only the date. Instead, we need to have all the information. Do you know what information is needed based on the API?

**AI Response (Summary):**
By analyzing the backend API, the AI determined the necessary parameters (`field_id`, `start_time`, `end_time`). It then modified the `CreateBookingPage.jsx` to:
1.  Fetch field details upon loading.
2.  Add a date selector.
3.  When a date is selected, call the `GET /api/fields/{id}/availability` endpoint to fetch available time slots.
4.  Display the available slots as clickable buttons.
5.  Handle the form submission by sending a `POST` request to `/api/bookings`.

**Analysis:**
This was one of the most complex interactions, requiring the AI to understand and orchestrate multiple data flows and state changes within a single component. It highlights the AI's strength in scaffolding complex, data-driven UIs.

### Interaction 5: Debugging and Refinement - The "Field Not Found" Error
This interaction is a prime example of the iterative debugging process. A feature did not work as expected, and the AI was used to diagnose and fix the issue.

**User Prompt:**
> It keeps telling me that it hasn't found the field. Check that the front-end and the API are communicating correctly. Also, check if you have used the names correctly.

**AI Response (Summary):**
The AI analyzed the data flow for the "Edit Booking" page and identified the error: the API response for a single booking (`GET /api/bookings/{id}`) contained a `field_id`, but not the full nested `field` object. The frontend code was incorrectly trying to access `booking.field.name`. The AI corrected the code by implementing a two-step fetch: first, get the booking to find the `field_id`, and then make a second call to `GET /api/fields/{field_id}` to get the field details.

**Analysis:**
This is a critical example of AI-assisted debugging. The AI was able to trace the data flow, compare the frontend's expectation with the backend's actual response, and implement the correct logic to resolve the discrepancy.

### Interaction 6: Improving User Experience - Custom Notifications and Modals
The final interactions focused on polishing the application's UI and UX, moving beyond basic functionality.

**User Prompt:**

3.  It then integrated these components into the main `Layout.jsx`, making them available to all pages through a shared context.

**Analysis:**
This demonstrates using the AI not just for logic, but for improving the user experience. The AI created reusable, styled components and integrated them into the existing architecture, resulting in a more professional and cohesive application.

### Interaction 10: Implementing Multi-Slot Booking
This interaction shows the AI's ability to implement a complex user-facing feature based on a simple request, including state management, UI updates, and price calculation.

**User Prompt:**
> Perfect, great job, it works perfectly. Now let's just implement the ability to choose multiple slots in the same field booking.

**AI Response (Summary):**
The AI refactored the `CreateBookingPage.jsx` component to:

**Analysis:**

### Interaction 11: Critical Debugging - The Timezone Bug (422 Error)
This was the most critical debugging session of the project. After implementing multi-slot booking, a persistent `422 Unprocessable Entity` error appeared, which the AI helped diagnose and resolve.

**User Prompt:**
> I'm getting a `422` error. I don't understand why it worked before and not anymore. What change did we make that started generating errors?

**AI Response (Summary):**
After several attempts to fix symptoms (CORS errors, 401 errors), the AI finally identified the root cause by analyzing the full error message: "The end time field must be a date after start time."
1.  **Diagnosis:** The AI explained that the browser was creating dates in the local timezone. When the frontend calculated the `end_time` and converted it to a string, this string, when interpreted as UTC by the server, could appear to be *before* the `start_time`.
2.  **Solution:** The AI proposed a crucial one-line fix in `CreateBookingPage.jsx`: force JavaScript to interpret the date as UTC by appending a `'Z'` to the date string (`new Date(lastSlot.replace(' ', 'T') + 'Z')`) before performing any calculations.

**Analysis:**
This interaction is a powerful example of AI-assisted debugging for a complex, non-obvious problem. The AI correctly traced the issue back to a subtle timezone mismatch between client and server and provided a precise, effective solution. This highlights the importance of handling dates consistently across different environments.

## 3. Frontend-Backend Connection Challenges

The following critical issues were identified and resolved during development:

1.  **Timezone Handling (`422` Error)**: Fixed a critical bug where the frontend generated an `end_time` that, due to timezone differences between the browser and server, was earlier than the `start_time`, causing a `422` validation error. The solution was to force date interpretation as **UTC** in the frontend by appending a `'Z'` to the date string before sending it to the backend.
2.  **Auth & CORS Errors (`401`/CORS)**: Resolved misleading CORS errors that were actually caused by an expired authentication token (`401 Unauthorized`). The request was being blocked by the authentication middleware before the CORS middleware could add the necessary headers. A pre-emptive check was added to the frontend to verify the token's validity before sending the request.
3.  **API Data Consistency**: Aligned the frontend to use property names exactly as provided by the API (e.g., `price_per_hour`), ensuring correct data display.
4.  **Post-Booking Navigation**: Corrected the redirect path after a successful booking to point to the correct route (`/bookings`).
